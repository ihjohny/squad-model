01 · The problem

Why normal agile breaks at this scale

Several squads building on the same payment, subscription and account services, all releasing on the same day.

30%

of the sprint goes to bug fixing

Edge cases never got reviewed, so "small" defects eat a third of the team's time.

20h

of meetings logged as coding

Clarification work disappears into dev hours, and the metrics stop meaning anything.

2x

the same tests, run twice

A backend deploys while QA is mid-run. The results are void, so everything gets retested.

Day 26

and a surprise in staging

Squad A changes a checkout payload. Squad B's subscription flow crashes, two days before submission.

💡
Note: none of this is a talent problem. It's what happens when six teams can't see what the other five are doing.

From PRD to the stores. Each phase ends with something concrete: an approved solution, signed-off features, a frozen backend.

02 · Squad Refinement

→

06 · The DAF

What happens in a DAF review

Half an hour of review here saves weeks of rework later.

BEFORE · THE WRITE-UP

The squad sends the doc

Sequence flows, failure handling, the security checklist, and the 4h task list. Shared at least a day before the slot.

→
IN THE ROOM · THE QUESTIONS

Hunting the gaps

The panel asks about the cases nobody planned for:

  • · gateway dies mid-payment?
  • · partial refund on retry?
  • · retry storm on a bad connection?
→
AFTER · THE SIGN-OFF

Approved, or back with notes

  • ✔ Approach approved
  • ✔ Task list checked
  • ✔ Dev hours confirmed
  • ✔ QA hours confirmed

Who's in the room: Core Product Leads Main Product Leads POL · Payments SOL · Subscriptions Platform Architects New endpoints get checked for security, token reuse and backwards compatibility before they exist.

The DAF decides The approach, the task breakdown, whether the estimates hold up
The SM locks Dev completion date, UAT handover date, release version and month. Based on business needs and the release plan, not on the review.
💡
Note: once the DAF has approved and the SM has scheduled, the scope is fixed. New requests go through estimation again. They don't come in through the side door.
07 · Docs before code

Two documents before any code

Both are short. Both are mandatory.

📐 THE ARCHITECT'S BOX SOLUTION one page, at grooming

A sketch of everything the feature touches:

Touched microservices Payment (POL) · Subscription (SOL) · Core Profile
Rough effort split e.g. 40% Frontend / 60% Backend
Downstream systems External gateways & telco billing
📜 THE SQUAD'S SOLUTION DOC Confluence, for the DAF review

The write-up the squad defends in the review:

  • ✔Sequence diagrams for the happy path and the failure paths
  • ✔What happens offline: flaky networks, timeouts, retry and caching rules
  • ✔The STRIDE security checklist for anything touching money or identity
  • ✔Blockers and the 4h task list, with dependencies called out
NO BOX, NO SPRINT  ·  NO DOC, NO DAF
💡
Note: an hour on these documents routinely saves a week of debugging. "I assumed the API worked differently" is what this is designed to prevent.
08 · Daily work

No task bigger than four hours

Short tasks mean problems surface at the next standup, not at the end of the sprint.

A 16-HOUR FEATURE, SPLIT
1 · DTO models & serialization tests
4.0h
2 · Repository layer & cache fallback
3.5h
3 · UI + viewmodel state binding
4.0h
4 · Error dialogs & analytics
3.0h

A developer can be blocked for a few hours, but never for days. Standup catches it within 24.

…AND HONEST TIME LOGS FEED THE DASHBOARD
Dev Time what ships

Coding, unit tests, PRs, review fixes. Target: 90% of the estimate actually delivered.

Refinement Time ≤ 20% of squad time

Meetings, KT sessions, docs, PO questions. Watched so it doesn't quietly swallow the sprint.

The central Jira dashboard tracks both, per engineer and per squad, weekly.
💡
Note: small PRs get reviewed in half an hour. Three-day PRs sit in the queue for days. That's most of the argument for the 4-hour rule right there.
09 · Quality

The 10% bug buffer, in practice

Bug fixing is part of the estimate. It's capped and watched, so it can't quietly eat the sprint.

Try it: the 10% buffer calculator live
40 Hours
10h quick task40h standard epic120h major feature
Max bug-fixing allowance: 4.0 Hours
DEV 90%
10%
Formula: Locked Dev Hours × 0.10
The rule: if a task needs more than 10% of its estimate in fixes, something is wrong with the design or the requirements. That's worth a conversation, not a silent overrun.
THE TWO OUTCOMES
✅ Within the buffer

Typos, styling, missed null checks. Fixed quietly, and the sprint never feels it.

🚨 Buffer blown

Fixing stops. Dev and lead sit down:

  • · were the edge cases tested locally?
  • · was the spec ambiguous?
  • · is there design debt to file?

A bug caught on the dev environment costs roughly a tenth of the same bug found after UAT. That gap is the whole reason for testing early.

💡
Note: if a fix takes ten hours, it was never a bug. The estimate or the design was wrong, and it's better to learn that in week one.
10 · When UAT finds a bug

Two kinds of bugs

One question decides who fixes it and what it counts against: does it also happen on the live app?

🐞 Bug found in UAT
→
Does it reproduce on live production?
NO ↓
A regression from this sprint
  • • Introduced by this squad's recent PR
  • • Fixed before UAT sign-off
  • • Counts against the QA leakage KPI (under 2%)
YES ↓
A pre-existing live bug
  • • SA confirms it exists in production
  • • Detached from the feature, sent to the Live Issue Pool
  • • Fixed through the squad's monthly quota

The split keeps the release date safe from old debt, measures QA only on what it could have caught, and still gets the old bugs fixed on a schedule.

💡
Note: if it happens in production, it was never your sprint's regression. Hand it over and keep your date.
