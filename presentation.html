The Problem Statement

Why Standard Agile Fails at Super-App Scale

When multiple squads build on top of core billing, payments, and account services, traditional 2-week sprints collapse.

SYMPTOMS OF UNGOVERNED SQUADS
  • • Cross-Product Breakages: Squad A alters a checkout payload; Squad B's subscription purchase silently crashes in staging.
  • • Moving Target QA: Backend microservices deploy while mobile QA is testing, producing ghost bugs and invalidating test runs.
  • • Invisible Work: Devs spend 20 hours in clarification meetings and log it as "coding time", distorting sprint velocity.
  • • Endless Bug Spills: Minor defects consume 30% of sprint capacity because edge cases were never audited upfront.
THE GOVERNED OPERATING MODEL
  • • ARB Gatekeeping: Central Payment (POL) & Subscription (SOL) architects approve solution docs before coding begins.
  • • Pre-Sanity Backend Freeze: All microservices deploy to production under TCAB clearance before mobile sanity begins.
  • • Time Classification: Clear separation between "Refinement Time" (discovery) and "Dev Time" (active coding).
  • • 5% Defect Cap: Mathematically limits bug-fixing overhead and triggers an immediate quality alarm when exceeded.
💡
Presenter Cue: Emphasize that governance is designed to protect developers: it guarantees that upstream microservice teams cannot break mobile features right before release.

5. Squad QA Testing Squad QA

9. Staged Rollout Stores + Ops

5% → 20% → 50% → 100% store rollout with Firebase Crashlytics radar (≥ 99.8% crash-free).

Architectural Standards

The "Box Solution" & Confluence Refinement

Eliminating ambiguity by designing contracts, failure modes, and threat models before coding.

PART 1: SOLUTION ARCHITECT'S "BOX SOLUTION"

Attached to the Jira ticket during PO grooming. Defines the system landscape and sets baseline estimation:

Touched Microservices Payment (POL) • Subscription (SOL) • Core Profile
Initial Effort Split 40% Frontend (Android & iOS) / 60% Backend
Downstream Systems External Payment Gateways & Telco Core Billing
PART 2: SQUAD CONFLUENCE SOLUTION SPEC

Authored by the squad developer during refinement. Required for ARB presentation:

  • ✔ Sequence Diagrams: Happy paths and network timeout / retry failure fallbacks.
  • ✔ Network Matrix: Offline caching, flaky 3G timeouts, exponential backoff with jitter.
  • ✔ STRIDE Threat Model: Analysis of mobile fraud, tampering, and API replay risks.
  • ✔ Blockers & 4h Tasks: Upcoming blocker analysis and granular task decomposition.
💡
Engineering Principle: Developers never code from a vague ticket description. Every feature begins with an architect's Box Solution and a documented Confluence specification.
Security Engineering

STRIDE Threat Modeling for Mobile Features

Mandatory threat analysis for financial transactions, subscriptions, and identity flows.

Threat Mobile Super-App Risk Required Countermeasure
Spoofing Fake mobile headers or spoofed MSISDN Signed mTLS tokens & SIM-binding validation
Tampering Modifying wallet balance in local SQLite / Preferences Strict server-side ledger; client cache is display-only
Repudiation User disputes duplicate bundle purchases Client-side idempotency keys passed to Payment Layer
Info Disclosure Leaking auth tokens to system logcat / crash logs R8/ProGuard obfuscation & Encrypted Keystore / Keychain
Denial of Service App retry storm when connection drops to 2G Exponential backoff, jitter, and local circuit breakers
Elevation of Privilege Direct invocation of internal telecom APIs Scoped OAuth2 permission checks enforced at BFF gateway
💡
Presenter Cue: STRIDE is not abstract security theory—it is practical edge-case thinking before writing code (e.g. "What if the user double-taps on 2G?").

Sprint Hygiene & Velocity

Time Engineering & The Central Jira Dashboard

Eliminating invisible work, chunking subtasks, and tracking true engineering velocity.

THE 4-HOUR GRANULAR SUBTASK RULE

In this operating model, no Jira task may exceed 4 hours. If a feature takes 16 hours, it must be split into 4 tangible subtasks:

1. DTO models & serialization unit tests 4.0h
2. Repository layer & room cache fallback 3.5h
3. UI composable & viewmodel state binding 4.0h
4. Edge-case error dialogs & analytics events 3.0h
Why it matters: Engineers can never be silently stuck for days. Any blocker is surfaced within 24 hours at daily standups.
TIME CLASSIFICATION TAXONOMY

Time logged in Jira is strictly segregated into high-value coding vs. discovery overhead:

Refinement Time Monitored Overhead

Time spent in discovery meetings, KT sessions, writing Confluence docs, and PO clarifications.

Dev Time (Active Coding) High-Value Velocity

Writing clean code, unit tests, building PRs, and resolving peer reviews. The primary velocity metric.

Central Jira Dashboard Squad Analytics

Rolls up squad boards: tracks Monthly Dev Completion, UAT Delivery alignment, quarterly volume, and Live Issue Quotas.

💡
Presenter Cue: Explain that 4-hour chunking is designed for developer peace-of-mind. Smaller PRs get reviewed in 30 minutes instead of sitting in review queues for days.
Defect Governance

Squad QA & The 5% Defect Buffer Rule

A mathematical safeguard ensuring bug fixing does not cannibalize sprint commitments.

Interactive 5% Buffer Calculator Live Simulation
40 Hours
10h (Quick Task) 40h (Standard Epic) 120h (Major Feature)
Max Permissible Bug Fix Time: 2.0 Hours
Formula: Locked Dev Hours × 0.05
Rule: Bug fixes on dev tickets are strictly budgeted. If a task requires more than 5% of its estimate to stabilize, it signals architectural debt or ambiguous acceptance criteria.
SHIFT-LEFT DEFECT DISCOVERY

Finding and fixing a bug on the Dev environment costs 10x less time than discovering it during UAT or in Production.

Within 5% Buffer (Green Path)

Minor typos, styling tweaks, edge-case null checks. Resolved smoothly by the developer without impacting sprint velocity.

Breaching 5% Buffer (Quality Alarm)

Triggers a constructive retro with the Squad Lead: Did the developer test edge cases locally? Was the API specification ambiguous?

💡
Engineering Principle: If a task takes 10 hours to debug, it wasn't a "bug"—it was an incomplete feature. The 5% rule protects engineers from silently taking blame for architectural flaws.
Acceptance & Triage

UAT Staging & Defect Bifurcation

How to eliminate friction between Squad QA and UAT while protecting quality metrics.

DEFECT TYPE A: RECENT REGRESSION / STORY BUG

The defect was directly introduced by the squad's recent code changes. Must be fixed by the squad developer before UAT sign-off.

Impacts Squad QA KPI: Measured as UAT Bug Leakage Rate. A higher volume of leaked bugs directly lowers the Squad QA's performance rating.
Incentivizes Squad QA to find all regressions before Staging handoff.
DEFECT TYPE B: PRE-EXISTING LIVE DEFECT

Discovered during UAT, but also reproduces on the current live production app. It is decoupled from the current feature release.

Transferred to Live Issue Pool: Solution Architect validates the defect. Squads draw from this pool to fulfill their mandatory Monthly Live Issue Quotas.
Protects feature delivery dates from legacy tech debt derailment.
💡
Engineering Principle: You never have to fear UAT discovering legacy bugs. Pre-existing issues are moved to the Live Issue Pool so sprint delivery remains 100% on schedule.
Release Operations

The Monthly Release Calendar & Backend Freeze

Decoupling microservice production deployments from mobile store reviews.

DAYS 01 - 18

Sprint Execution

Dev implementation, PR code reviews, and testing in the Dev Environment via VPN.

DAY 19

Staging / UAT Cutoff

Features deployed to Staging; business acceptance runs on VPN-secured builds.

DAYS 21 - 22

TCAB & BE Live Freeze

All backend microservices deploy to LIVE production under TCAB before sanity starts.

DAYS 23 - 28

Dual-Gate Sanity

Release candidate branch verified by QA Sanity Pool, followed by final commercial UAT sign-off.

Branch Consolidation & Rotating Release Team

Squad-Wise Branches: Squad Leads merge completed items into their respective squad release branches.
Consolidated Sanity: Final sanity candidate branch created by merging all squad main release branches.
Rotating Dev Team: Monthly rotating senior squad members manage branch merges and store submission.
💡
The Cardinal Rule: Mobile sanity testing NEVER starts against a changing backend. Backend microservices freeze and deploy to production first; mobile sanity runs second.
